# Session: Issue #865 — CUDA fallback fail-closed fix

## Phase 1: Problem statement (gate satisfied, no re-creation needed)

Issue #865 was reopened 2026-09-06 by the human with concrete evidence:
PR #875's first compiling CUDA-feature build (CI run 34050070656) unmasked a
pre-existing bug in #866's fallback path. On a GPU-less runner, with `cuda`
feature compiled in and backend effectively `auto` or `cuda`+`fallback: cpu`:

```
CUDA unavailable ... libcublasLt.so.12: cannot open shared object file
```

followed by:

```
embed_index: failed to fresh-reopen persisted graph immediately before semantic publication
```

The CUDA-unavailable condition is not caught and demoted to CPU cleanly at
provider-construction time — it propagates into the embed/publish sequence
and corrupts/blocks graph reopen right before semantic publication, instead
of running cleanly on CPU per the `fallback: cpu` policy.

Acceptance criteria: see issue body (full CUDA backend feature, already
delivered by #866). This PR's scope is narrower — just the fail-closed/
fallback-demotion bug on the GPU-less path, per the human's brief.

## Phase 3: Solution space

**Code read:** `src/embed/config.rs`, `src/embed/cuda_encoder.rs`, `src/embed/real.rs`
(specifically `new_model_with_config`, lines ~979-1170, and the
`index_all_generation` persisted-graph-reopen-before-publication sequence,
lines ~2900-3245), `src/embed.rs`.

### Root cause (two compounding gaps, not one)

**A. Logic gap — explicit `backend: cuda` never consults `fallback` at all.**
In `new_model_with_config` (`real.rs`), automatic CUDA→CPU/Metal demotion is
implemented *only* inside the `EmbeddingBackend::Auto` branch (lines 985-997):
it recurses with `backend = Cuda`, and on `Err` logs
`tracing::warn!("CUDA unavailable for auto embedding backend; falling back
according to policy: {error}")` and falls through to the Metal/CPU path.
But the separate `if config.backend == EmbeddingBackend::Cuda` branch
(lines 1001-1045, reached directly when backend is explicitly `cuda`) has
**no reference to `config.fallback` whatsoever** — any `CudaEncoder::new()`
error there is wrapped in `anyhow::anyhow!(...)` and returned as `Err`
unconditionally. So `backend: cuda, fallback: cpu` behaves identically to
`fallback: error` today. This is a real, independently-fixable bug, but by
itself it only explains a clean early `Err` — not the corrupted persisted-graph
reopen the issue reports.

**B. Architectural gap — CUDA-unavailability detection depends on ORT
returning `Result::Err` from in-process construction, and that is not a safe
assumption for a missing native shared-library dependency.**

`CudaEncoder::new()` already does the right *shape* of thing in isolation: it
builds the ORT session with `.with_execution_providers([CUDA::default()...
.build().error_on_failure()])` (eager: forces a provider-registration error
instead of silently omitting CUDA), then runs two real `encode()` calls plus
`observe_output_device()` — i.e. it already contains a "probe encode" before
returning any usable encoder or evidence. In principle this should surface
`libcublasLt.so.12: cannot open shared object file` as a normal `anyhow::Error`
that propagates cleanly back through `new_model_with_config`'s `?`/`match`.

The problem is *where* that construction runs: in-process, in the same
address space as the rest of the `embed_index` pipeline, including the shared
LanceDB persisted-graph store that `index_all_generation` later reopens at
`crate::server::load_graph_from_lance(repo_root)` (real.rs:3235, guarded by
`.context("failed to fresh-reopen persisted graph immediately before semantic
publication")`). ORT's CUDA execution provider is not one self-contained
library — registering it dynamically loads `libonnxruntime_providers_cuda.so`,
which itself depends on `libcublasLt.so.12`/other CUDA/cuBLAS runtime
libraries. When those are absent (GPU-less runner), the failure occurs inside
onnxruntime's own C++ provider-factory / dynamic-loader path. Whether that
class of failure comes back as a well-behaved `OrtStatus` (→ safe `Result::Err`
in the `ort` crate) or as something that crosses the `extern "C"` FFI boundary
uncaught (C++ exception unwinding into Rust → UB/abort, or a hard process
fault) is not something this codebase controls, verifies, or defends against
today. `.error_on_failure()` only guarantees eagerness for the class of
failures ORT itself models as provider-option validation; it does not
guarantee immunity from native-library-load faults escaping as anything other
than a clean `Result::Err`.

If (as the reproduction evidence — a corrupted/blocked persisted-graph reopen
appearing *after* the CUDA-unavailable log line, not a clean early return —
suggests) the real failure mode is a process-level fault rather than a
returned `Err`, then no amount of additional `match`/`?`/`catch_unwind` logic
*inside the same process* can guarantee synchronous, safe demotion, because
the fault can take down the process (and any LanceDB writes in flight or
about to be finalized in that same process/working directory) before Rust
control flow ever resumes. This is the "architectural, not patchy" root
cause: CUDA-availability must be established out-of-process, before any
pipeline side effects begin, so a native fault is contained to a throwaway
process instead of the real `embed_index` run.

### Candidate solutions

1. **Band-Aid — fix the explicit-`cuda`-branch logic gap only (A above).**
   Make the `EmbeddingBackend::Cuda` branch consult `config.fallback` the same
   way `Auto` does (extract a shared `try_cuda_then_fallback` helper used by
   both branches). Trivial, low-risk, and closes the literal "explicit cuda +
   fallback:cpu is silently treated as fallback:error" bug. Does **not**
   address root cause B: if the underlying ORT failure is a process fault
   rather than a catchable `Err`, this fix never runs — the same corruption
   reproduces under `auto` today (which already funnels through the fixed
   code path) per the issue's own reproduction.

2. **Local optimum — wrap `CudaEncoder::new()` in
   `std::panic::catch_unwind`, plus fix (A).** Catches ordinary Rust panics
   that occur inside the encoder construction/probe-encode path (e.g. a
   `.expect()`/`ensure!` turned into a panic somewhere in the call graph) and
   converts them into a normal demotion. Better coverage than (1), and easy to
   land alongside it. But `catch_unwind` is documented as **not** guaranteed
   to catch unwinding that crosses a foreign (`extern "C"`) function boundary —
   Rust's own panic runtime aborts the process in that case rather than
   unwinding into `catch_unwind` — and it cannot catch a real signal/segfault
   from a native library at all. So it narrows the blast radius without
   closing it, and gives false confidence that "CUDA init is now safely
   probed" when the specific failure class in the bug report
   (`cannot open shared object file` from a missing CUDA runtime lib, surfaced
   through onnxruntime's own C++ provider loader) is exactly the kind of fault
   `catch_unwind` is least likely to help with.

3. **Reframe — probe CUDA availability in an isolated child process before
   doing anything else.** Before `new_model_with_config` ever runs the real
   `CudaEncoder::new()` in-process for an `auto` or `cuda` request, spawn a
   short-lived subprocess (re-exec `std::env::current_exe()` with a hidden
   `--probe-cuda-encoder` mode, mirroring the existing self-exec pattern
   already used in `src/adr.rs`'s smoke-run path and `src/structural_cache.rs`)
   that does exactly what `CudaEncoder::new()` does today (session build +
   probe encodes) and reports success/failure via exit code + a small
   stdout/stderr capture. The parent process treats "child exited 0" as CUDA
   usable and proceeds to build the *real* `CudaEncoder` in-process (now known
   safe), and treats "child exited nonzero, or was killed/aborted/segfaulted"
   as CUDA unavailable and demotes per `fallback` policy — uniformly for both
   `auto` and explicit `cuda + fallback: cpu`. Because the probe runs in its
   own address space, a native fault there cannot corrupt the parent's
   in-flight LanceDB state, and the parent's decision to demote happens
   *before* any `embed_index`/graph-persistence side effects start, closing
   root cause B directly. Cost: one extra process spawn per cold-start
   CUDA/auto attempt (bounded, not per-batch), plus a small amount of new
   subprocess-plumbing code — but that shape (self-exec probe subcommand)
   already exists in this codebase for an analogous "prove an external/native
   thing works before trusting it" need.

4. **Redesign — extend the "stage, verify, atomically promote" discipline
   `index_all_generation` already uses for semantic generations (write to a
   staging root, `create_fts_index_strict`, fresh-reopen-and-verify, then
   `promote_staging_generation`) down into whatever persistence layer owns
   `load_graph_from_lance`'s target (the code-graph LanceDB, not the
   embedding-generation LanceDB), so that *no* interruption of *any* kind
   (CUDA fault, OOM-kill, CI runner timeout/SIGKILL, disk full) can ever leave
   that store in a state that fails a later fresh-reopen.** This is the right
   long-term invariant — "a half-finished write should never be visible to a
   fresh reopen" is a general property the persisted-graph layer should have
   regardless of CUDA — but it is a larger change reaching outside
   `src/embed/*` into the graph-persistence/scan layer, and is not required to
   close #865's narrower scope (per Phase 1: "just the fail-closed/
   fallback-demotion bug on the GPU-less path").

### Recommendation

**Chosen: Option 3 (isolated CUDA availability probe subprocess), combined
with Option 1's logic fix (uniform `fallback` handling for both `auto` and
explicit `cuda`) so both configurations demote through the same code path.**
Option 4 is noted as a good defense-in-depth follow-up (tracked separately,
not required for #865's scope) since a hardened graph-persistence layer would
make the *symptom* (corrupted reopen) impossible even if some future fault
source were missed, but it's a materially larger change than this issue's
brief.

**Why not the others alone:** (1) fixes a real bug but doesn't address why
the failure corrupts the persisted graph instead of returning `Err` cleanly —
i.e. it fixes the code path that's provably reachable only when ORT behaves
well, which isn't the failure mode in evidence. (2) narrows but doesn't close
the blast radius, and specifically fails to help with the exact failure class
reported (missing shared library dependency surfaced through a native
provider loader). (4) is the right invariant at a higher altitude but is
out of scope for this issue and touches code outside `src/embed/*`.

**Known trade-offs accepted:** one extra process spawn on cold-start
CUDA/auto attempts (not per-request/per-batch, since the resulting
`CudaEncoder` is reused for the life of the resolved model); a small amount of
new subprocess-plumbing code in `src/embed/real.rs` (or a new
`src/embed/cuda_probe.rs`) following the existing self-exec pattern in
`src/adr.rs`.

### Verification plan

**Reproduce first (confirm the bug on this branch before changing anything):**
- On a GPU-less machine/CI runner (or by unsetting/renaming
  `libcublasLt.so.12` locally, e.g. via `LD_LIBRARY_PATH` pointing at an empty
  dir, or running in a container without CUDA runtime libs installed), build
  with `--features cuda` and run with `RNA_EMBEDDING_BACKEND=auto` (default)
  and separately `RNA_EMBEDDING_BACKEND=cuda RNA_EMBEDDING_FALLBACK=cpu`
  against a real repo checkout (`rna scan` / whatever drives
  `EmbeddingIndex::index_all` end to end).
- Confirm today's failure signature reproduces: the
  `libcublasLt.so.12: cannot open shared object file` log line, followed by
  the persisted-graph reopen failure at
  `.context("failed to fresh-reopen persisted graph immediately before
  semantic publication")` (or an equivalent fresh-reopen context earlier in
  `index_all_generation`), rather than a clean successful CPU-backed
  `embed_index` run.

**Confirm the fix — unit tests:**
- Extend `src/embed/real.rs`'s existing `auto_error_does_not_require_compiled_
  cuda_backend` test family (around line 6625) with a case for
  `backend: cuda, fallback: cpu` on a build/host where CUDA construction fails
  (feature compiled but no device/libs), asserting it returns a CPU/Metal
  `EncoderModel` rather than `Err`, mirroring the existing `auto` coverage.
- Add a unit test around the new probe subprocess boundary: a fake/forced
  probe failure (e.g. inject a probe binary path or env override that always
  exits nonzero) demotes cleanly for both `auto` and `cuda+fallback:cpu`, and
  a forced probe success + real CUDA absent (i.e. simulate a probe/parent
  mismatch) still fails safe rather than assuming success.
- Confirm `identity_flags()`/`effective_backend` reporting reflects the
  demoted backend truthfully after a probe failure (existing generation
  identity/attestation tests around line 6580-6710 already assert this shape
  for the current paths; extend rather than duplicate).

**Confirm the fix — live run:**
- On the same GPU-less environment used to reproduce the bug, rerun
  `rna scan` (or the direct `embed_index` entry point) with `--features cuda`
  and `RNA_EMBEDDING_BACKEND=auto` and `cuda`+`fallback:cpu`, and confirm:
  - The run completes successfully end to end (no fresh-reopen failure).
  - `runtime_diagnostic()`/logs report `effective_backend=cpu` (or `metal` if
    applicable) with the CUDA-unavailable reason recorded, not silently
    swallowed.
  - The persisted graph and semantic generation are both readable/queryable
    afterward (`rna search`), i.e. no corruption from this run.
- On a real GPU host (NUC or equivalent, per #866's original verification
  plan), confirm CUDA still initializes and is used normally (no regression
  to the happy path) — the probe subprocess should exit 0 and the parent
  should proceed to build the real in-process `CudaEncoder` exactly as today.
