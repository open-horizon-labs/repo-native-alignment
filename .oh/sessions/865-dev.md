# Add native CUDA embedding backend and explicit device configuration

## Problem

RNA's primary embedding path is currently implemented with `metal-candle`: it can use Apple Metal or fall back to CPU, but the NUC14 deployment has no native CUDA path. The host has an NVIDIA RTX 3060 Ti, and OpenVINO also sees the Intel Arc GPU, but RNA's current `fastembed`/ONNX Runtime feature closure does not enable CUDA or OpenVINO execution providers.

As a result, repository-wide embedding/indexing on the NUC cannot use the available NVIDIA accelerator, and the selected execution device is not an explicit, observable configuration contract.

## Desired behavior

RNA should use the best explicitly supported embedding backend on the host:

- `cuda` uses the NVIDIA GPU and fails clearly if CUDA support/runtime/device initialization is unavailable.
- `cpu` forces CPU execution.
- `auto` selects the supported accelerator according to documented precedence and reports the effective backend.
- Existing `metal` behavior remains valid on Apple Silicon.
- CPU fallback is never silent when a user explicitly requests CUDA.
- Semantic generation identity records the requested/effective backend, provider, device, and materially relevant execution options so incompatible indexes cannot be reused.

## Scope

- Add a CUDA-capable primary embedding backend using the existing ONNX Runtime/fastembed direction.
- Add the required Cargo feature closure (including `ort/cuda`) and document runtime CUDA/cuDNN requirements.
- Add configuration via `.oh/config.toml`, with equivalent CLI/environment support where appropriate:
  - backend/device: `auto | cpu | cuda | metal`
  - CUDA device ordinal
  - fallback policy: `cpu | error`
  - batch size: adaptive default or fixed value
  - initial CUDA memory/arena tuning only where useful and stable
- Report requested backend, observed provider, device index/name, precision, batch policy, and fallback status.
- Include backend/provider/device/options in semantic generation identity and validation.
- Verify on the NUC's RTX 3060 Ti with real repository indexing and semantic search.
- Preserve the existing model, vector dimension, preprocessing, LanceDB schema, retrieval behavior, and reranking behavior unless required by the backend migration.
- Add tests for parsing, precedence, CPU isolation, strict CUDA failures, provider selection, identity separation, and MCP-visible readiness.

## Out of scope

- Multi-GPU scheduling.
- TensorRT.
- Automatic driver/toolkit installation.
- CUDA support for unrelated workloads.
- OpenVINO implementation beyond leaving a clean provider seam; Arc/OpenVINO can follow after CUDA.

## Acceptance criteria

- [ ] A CUDA-enabled build compiles with an explicit Cargo feature and does not claim CUDA support when built without it.
- [ ] The primary MiniLM embedding model can execute through CUDA on the RTX 3060 Ti.
- [ ] `backend=cuda` fails closed on missing build support, missing CUDA/cuDNN runtime, or unusable device; it never silently falls back.
- [ ] `backend=cpu` never initializes CUDA or Metal.
- [ ] `backend=auto` has documented precedence and reports the effective provider/device; CPU fallback is explicit.
- [ ] Configuration accepts and tests backend, device, fallback policy, and batch size.
- [ ] Diagnostics expose requested/effective backend, provider, device, precision, batch policy, and fallback without secrets.
- [ ] Semantic generation identity differs across CPU/CUDA/Metal and materially different CUDA settings; stale incompatible generations are rejected.
- [ ] Existing CPU and Metal behavior remains compatible when no new configuration is supplied.
- [ ] Real NUC verification shows CUDA is actually executing, not merely registered while work runs on CPU.
- [ ] MCP readiness/status exposes the effective embedding backend and failure state.
- [ ] Relevant tests, clippy/checks, and documentation pass.

## Solution Space
**Updated:** 2026-09-04

**Problem:** RNA needs a native, observable CUDA MiniLM execution path on the RTX 3060 Ti without breaking CPU/Metal users or reusing semantic generations produced by an incompatible runtime.

**Key constraint:** the current encoder is Candle/metal-candle, while the requested CUDA direction is the existing fastembed/ONNX Runtime path. The system must fail closed for explicit CUDA, preserve the existing 384-dimensional MiniLM contract, and deliver effective runtime state through MCP.

### Repository and dependency evidence

- `Cargo.toml` currently makes `metal-candle`, `candle-core`, `fastembed`, and Lance FTS part of one `embeddings` feature; `metal` adds Candle Metal/Accelerate. There is no ORT dependency feature closure for CUDA.
- `src/embed/real.rs` initializes `metal_candle::EmbeddingModel` and chooses Candle Metal or CPU. Its `DeviceAttestation` currently only distinguishes `candle-metal` and `candle-cpu`; the embedding pipeline has hard-coded write batches plus a separate adaptive path.
- `src/embed/generation.rs` already has durable semantic identity, generation manifests, device attestation, validation, and fresh-reopen verification seams. Identity flags and attestation are the natural compatibility boundary, but currently encode Metal-oriented assumptions (`require_metal`).
- Readiness already flows through `src/server/state.rs`, operation reports, scan/enrichment summaries, and MCP handlers. The missing work is adding effective encoder contract/failure detail to those existing delivery paths.
- Cached `fastembed 5.17.2` exposes `TextEmbedding` and `TextInitOptions::with_execution_providers`. It re-exports ORT's `ExecutionProviderDispatch`; user-defined and downloaded models use ORT sessions.
- Cached `ort 2.0.0-rc.12` exposes `ep::CUDA` / `CUDAExecutionProvider`, `with_device_id`, strict registration via `error_on_failure`, and CUDA/cuDNN dynamic-library loading. Its `cuda` Cargo feature is separate from fastembed's `cuda` feature; fastembed's feature enables Candle CUDA for its Candle-backed model families and is not the required ORT closure.

### Candidates considered

| Option | Level | Approach | Main trade-off |
|---|---|---|---|
| A | Local optimum | Extend the current Candle backend with CUDA | Lowest apparent churn, but creates a second model/runtime contract and does not provide truthful ORT provider reporting. |
| B | Band-aid | Keep fastembed defaults and rely on provider/environment auto-selection | Cannot guarantee CPU isolation, strict CUDA failure, selected ordinal, or identity separation; silent CPU execution remains possible. |
| C | Reframe | Put an RNA-owned explicit provider/configuration seam around fastembed TextEmbedding | Medium integration work and ORT runtime packaging complexity, but directly matches the requested MiniLM/ORT path and makes policy observable/testable. |
| D | Redesign | Build a separate custom ORT encoder, including tokenizer/pooling/model loading | Maximum control, but duplicates fastembed behavior and increases compatibility and maintenance risk without solving an additional issue requirement. |

### Evaluation

**Option A: Candle CUDA**

- Solves stated problem: Partially. It could accelerate inference, but it diverges from the requested fastembed/ONNX Runtime direction and makes provider truth difficult.
- Implementation cost: Medium; maintenance burden: High because two backend model contracts would coexist.
- Second-order effect: More identity and asset variants, more platform-specific failures, and no clean ORT provider evidence.

**Option B: implicit fastembed/provider selection**

- Solves stated problem: No. It does not establish explicit backend/device/fallback semantics.
- Implementation cost: Low; maintenance burden: High because behavior depends on build/runtime defaults.
- Second-order effect: the most dangerous failure mode—CUDA requested or assumed while CPU actually executes—would be hard to diagnose and could poison generation reuse.

**Option C: explicit ORT provider seam (recommended)**

- Solves stated problem: Yes, subject to real NUC verification. It supports MiniLM through the existing fastembed API, explicit CUDA ordinal, CPU-only construction, strict errors, and auto fallback.
- Implementation cost: Medium; maintenance burden: Medium. It requires feature wiring, typed config precedence, runtime attestation, and readiness plumbing.
- Second-order effect: keeps one model/preprocessing/vector contract and creates a reusable provider seam for a future OpenVINO backend without implementing OpenVINO now.

**Option D: custom ORT encoder**

- Solves stated problem: Yes, but over-scopes it.
- Implementation cost: High; maintenance burden: High due to duplicated tokenizer, pooling, model asset, and output semantics.
- Second-order effect: likely semantic drift from current vectors and a larger compatibility migration surface.

## Recommendation

**Selected:** Option C — explicit ORT provider seam around fastembed TextEmbedding.

**Level:** Reframe/local redesign of the encoder boundary.

Use typed settings with `.oh/config.toml` as the repository contract and equivalent CLI/environment overrides. Resolve `backend`, CUDA ordinal, fallback policy, batch policy, and stable provider options once per embedding generation. Construct only the requested provider list: CPU-only for `cpu`; strict CUDA EP with the ordinal and registration failure for `cuda`; documented CUDA → Metal → CPU selection for `auto`; and preserve Metal behavior for `metal` on Apple Silicon. Treat successful session/model initialization and a real embedding probe as the attestation boundary, not merely EP registration.

Record requested/effective backend, observed provider, device ordinal/name, precision, batch policy, fallback status, and materially relevant provider options in diagnostics and semantic identity. Reject old or mismatched generations through identity validation. Feed the same runtime report into operation/readiness state so MCP can distinguish ready, degraded fallback, unavailable, and failed strict CUDA states without secrets.

**Accepted trade-offs:**

- CUDA builds will require compatible ORT CUDA 12 and cuDNN 9 runtime libraries; RNA reports actionable errors but does not install them.
- CPU fallback in `auto` remains a deliberate degraded state and must be visible in identity/readiness; explicit CUDA never falls back.
- Existing Metal code may need an adapter behind the common encoder contract rather than being deleted, preserving Apple compatibility while reducing future backend branching.

### Implementation and verification notes

- Add a dedicated ORT dependency/feature closure; do not confuse `fastembed/cuda` with `ort/cuda`.
- Keep model name, tokenizer/preprocessing, 384 dimension, LanceDB schema, retrieval, and reranking unchanged.
- Replace hard-coded encoder batch constants with one resolved batch policy, retaining adaptive behavior as the default and including the policy in identity.
- Test parsing/precedence, feature-disabled CUDA, CPU isolation, strict missing-runtime/device failures, provider/ordinal selection, fallback diagnostics, identity separation, and MCP-visible readiness.
- Verify on the NUC with a real repository index and semantic query, provider/device telemetry plus GPU activity, then exercise CPU and Apple Metal compatibility paths.

## Execute
**Updated:** 2026-09-04
**Status:** complete-with-blocker

Implemented the initial CUDA seam in the specified worktree: added the explicit
`cuda` Cargo feature with a direct `ort/cuda` closure, typed embedding config
from `.oh/config.toml` plus environment overrides, fixed/adaptive batch policy,
identity flags, and a strict fastembed MiniLM CUDA provider construction with a
real embedding probe. The primary encoder now supports a CUDA fastembed variant
while retaining Candle CPU/Metal variants.

RNA MCP tools were not exposed in this session; targeted `rg`/shell inspection
was used as a documented friction fallback. The first CUDA build check is
currently blocked by the machine's missing OpenSSL development headers
(`openssl/opensslv.h`) before Rust compilation reaches this change.

  headers (`openssl/opensslv.h`); setting the available library/include paths
  confirmed the headers are absent.

  failure, before Rust tests compile.
