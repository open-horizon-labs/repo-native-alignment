## Phase 1 verification (done before issue creation)

Findings from reading the actual `main` tree (7cebf90), not the salvage report's claims:

1. **CORRECTED (was wrong): `content.unresolved_anchor` DOES exist.** It lives at
   `src/extract/markdown.rs:750` and validates markdown *heading* anchors (documented in
   `docs/content-source-contract.md:93`, a separate content-pack diagnostic corpus). The
   original grep here was a false negative — the diagnostic exists and its metadata
   convention (`validation_status`, `diagnostic_code`, `diagnostic_severity`,
   `diagnostic_message`) is exactly what #891 reuses for the new `content.dead_code_anchor`
   code (see "Phase 2+ log" below). This module is a sibling of an existing pattern, not a
   wholly new one — correcting the "net-new detection logic" framing in the original
   conclusion below.

2. **`src/extract/markdown.rs` (1882 lines) already extracts:**
   - `code_spans: Vec<String>` per chunk — backticked inline code spans (e.g. `` `Config` ``,
     `` `Config::new()` ``), stored as `metadata["code_spans"]` (comma-joined string).
   - `links: Vec<(String, String)>` per chunk — markdown `[text](dest)` link text/dest pairs.
   - `emit_link_edges` (line ~278): for each chunk's links, skips external URLs/mailto/anchor-only
     (`#foo`)/empty; strips `#anchor` suffix from the dest path; resolves relative paths against
     the markdown file's own directory (handling `..`, see line ~503); emits a `References` edge
     from the section node to a **synthetic target node for the linked file** if the target
     path exists on disk relative to repo root — this is existence-checked for the *file*, but:
     - does NOT check line numbers embedded in prose text like `path/to/file.rs:123`
     - does NOT check backticked symbol names against the graph
     - does NOT check numeric constants
     - only checks proper markdown link syntax `[text](path)`, not bare-word references like
       `src/foo.rs:42` in prose (which is ripwire's primary target and this issue's requirement a).
   - ADR validation/backreference passes (line ~1394, ~1536) link ADR frontmatter to exact Rust
     test paths declared in frontmatter, scoped per `NodeId.root` — a narrower, ADR-specific
     mechanism, not a general doc-drift check.

3. **Diagnostic node pattern**: `NodeKind::Other("diagnostic")` is the existing convention for
   surfacing findings as graph nodes. Built by `LspEnricher::build_diagnostic_nodes` in
   `src/extract/lsp/mod.rs` (~line 1654), called from `src/extract/lsp/passes.rs`. Diagnostic
   metadata columns are defined in `src/server/store/metadata_keys.rs` (~line 39) and stored via
   `src/graph/store.rs` (~line 31, 73, 137: `diagnostic_severity` etc). `src/server/helpers.rs`
   (~line 499) surfaces diagnostic-specific metadata to callers. This is the pattern to reuse for
   doc-drift findings if we want them to be graph-queryable/persisted; it currently exists only
   for LSP diagnostics (rust-analyzer), not for any RNA-internal analysis pass.

4. **`.oh/` artifact parsing** (`src/oh/mod.rs`, 333 lines): loads `.oh/{outcomes,signals,
   guardrails,metis}/*.md`, splits YAML frontmatter from body, no structured reference/target
   resolution inside the body — frontmatter is a flat `BTreeMap<String, serde_yaml::Value>`.
   No `rna.relationships[].target.uri` field exists anywhere in the current schema.

5. **CORRECTED (was wrong): `src/oh_reference.rs` DOES exist on `main`.** It was added by
   commit `70699832` ("Resolve advisory Open Horizons references (#864)", 2026-08-30) and is
   still present, exposing a `resolve_references` MCP tool that resolves `oh://v1/context/...`
   identities against an *external* Open Horizons advisory service. This is about resolving IDs
   against a remote advisory system, not code-graph symbol resolution, so it is still not
   directly reusable for #891's file/symbol drift detection — that conclusion from the original
   pass stands even though the "file no longer exists" premise was wrong (re-verified with

6. **`computed-but-not-delivered` guardrail** exists at
   `.oh/guardrails/computed-but-not-delivered.md` — doc-drift findings must be surfaced via CLI
   and MCP (not just computed silently), per this guardrail, matching the issue's ask.

**Conclusion:** this is net-new detection logic, not an extension of an existing pass. It should:
- add a new markdown-drift analysis pass (on-demand, not part of default `scan`, per the issue's
  performance requirement) that scans already-extracted markdown metadata (code_spans, raw body
  text for `file:line` / bare path patterns) plus the code graph (symbols by file, file existence,
  file line counts) to produce drift findings.
- represent findings using the existing `NodeKind::Other("diagnostic")` convention (extended with
  a new diagnostic source, e.g. `"doc-drift"`) so CLI/MCP surfacing reuses existing plumbing
  (`build_diagnostic_nodes`-style helper, `metadata_keys.rs` columns, `helpers.rs` surfacing) —
  final call to be validated in solution-space phase against what "CLI and MCP parity" pattern
  already exists for on-demand (non-scan) reports.

## Additional verification: CLI/MCP parity pattern

- RNA currently exposes only **4 MCP tools** (`src/server/tools.rs`): `outcome_progress`,
  `search` (multi-mode: neighbors/impact/reachable/tests_for/cycles/path via `mode` param),
  `list_roots`, `repo_map`.
- The CLI (`src/main.rs`) has more subcommands than MCP tools — e.g. `Adr { Compile, Validate,
  Audit }` is **CLI-only**, no MCP tool wraps it. So "CLI and MCP parity" is not a universal
  norm in this codebase today; some on-demand analyses are deliberately CLI-only. This needs to
  be weighed explicitly in solution-space: either (a) add doc-drift as a new CLI subcommand only
  and justify no MCP tool (risk: violates the issue's explicit "CLI and MCP parity" requirement
  and the `computed-but-not-delivered` guardrail's "visible to agents" intent — MCP is the
  agent-facing surface), or (b) add both a CLI subcommand and an MCP surface, likely as a new
  `mode` on the existing `search` tool (cheapest reuse of existing plumbing) or a new dedicated
  tool. Given the issue explicitly requires MCP parity, plan (b) is very likely correct — call
  this out for oh-solution-space to decide the exact shape.
- `scan` has a `--timings` flag already (`ScanArgs.timings` in `main.rs`) — reuse this exact flag
  name/pattern for the before/after cost report the issue asks for.
