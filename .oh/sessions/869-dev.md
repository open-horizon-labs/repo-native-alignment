## Aim

Agents indexing repositories on the NUC can use the integrated Intel Arc GPU for
primary embeddings, with truthful device identity and an explicit CPU fallback.
This is a separate capability from CUDA PR #866.

## Problem Statement

RNA's primary embedding implementation is Candle/Metal-oriented. The NUC's
OpenVINO runtime can execute on Intel Arc, but RNA has no explicit OpenVINO
backend, provider selection, or device attestation for that path. Success means
real MiniLM-L6-v2 `[1,384]` execution on explicit OpenVINO `GPU.0`, with CPU
fallback and cache identity semantics preserved.

## Problem Space

- OpenVINO 2026.3.1 detects the Arc device with `FULL_DEVICE_NAME` containing
  `Intel`; `GPU.0` is the required explicit target.
- Unqualified `GPU` is forbidden because it can resolve to the wrong OpenCL
  device when multiple accelerators are visible.
- `fastembed` is already a dependency and exposes an injected ORT execution
  provider seam; compatibility with the locked ORT release must be verified.
- Existing semantic generation and MCP/reporting code must continue to see
  provider, device, readiness, fallback, and identity consistently.
- CUDA PR #866 is out of scope and must not be modified or stacked upon.

## Solution Space

### Candidates Considered

| Option | Level | Approach | Trade-off |
|---|---|---|---|
| A | Local optimum | Add OpenVINO-specific code beside the Candle model and select it by a feature flag | Duplicates model lifecycle and risks divergent identity/readiness behavior |
| B | Reframe | Generalize the embedding encoder behind a backend trait, retaining Candle Metal/CPU and adding ORT OpenVINO | Moderate refactor, but one lifecycle and one attestation contract |
| C | Local optimum | Use OpenVINO as a process-wide default provider and let runtime auto-select devices | Simple, but violates explicit Intel targeting and makes identity non-deterministic |
| D | Redesign | Make all accelerator backends independently pluggable runtime providers | Best long-term shape, but too broad for a focused 1-4 hour backend addition and raises compatibility risk |

### Evaluation

**Option A — Parallel implementation**

- Solves the stated problem: Yes.
- Implementation cost: Medium.
- Maintenance burden: High; model loading, dimension checks, diagnostics, and
  fallback policy can drift between backends.
- Second-order effects: Provider identity can be reported differently by each
  path, creating stale vectors or misleading MCP readiness.

**Option B — Shared encoder boundary**

- Solves the stated problem: Yes.
- Implementation cost: Medium/high.
- Maintenance burden: Medium/low; common identity and execution policy remain
  centralized.
- Second-order effects: Requires careful preservation of current Candle behavior
  and test fixtures, but enables future backend-specific selection.

**Option C — Runtime auto-selection**

- Solves the stated problem: Partially.
- Implementation cost: Low.
- Maintenance burden: High because host/provider resolution is implicit.
- Second-order effects: Can select NVIDIA or CPU instead of Intel Arc and make
  cache reuse unsafe across machines.

**Option D — Provider plugin redesign**

- Solves the stated problem: Yes.
- Implementation cost: High.
- Maintenance burden: Low after completion, high migration risk now.
- Second-order effects: Expands the diff into a framework change unrelated to
  proving Arc support.

## Recommendation

**Selected:** Option B — Shared encoder boundary

**Level:** Reframe

Use the existing fastembed/ORT seam for the OpenVINO implementation, but put
backend selection and the resulting attestation behind the same embedding
facade used by Candle. Build OpenVINO behind an explicit optional Cargo feature;
resolve an Intel device by `FULL_DEVICE_NAME`, pass `GPU.0` explicitly to the
OpenVINO execution provider, run a real `[1,384]` probe, and only then expose
the backend as ready. On unavailable/unsupported provider or device, apply the
configured CPU fallback or return a clear error. Include provider, device,
model, dimension, and relevant configuration in embedding identity.

**Accepted trade-offs:**

- OpenVINO/ORT runtime libraries remain a host prerequisite and are not bundled
  into the default artifact.
- The backend requires a feature-enabled build and an explicit runtime probe;
  CPU remains the portable default/fallback.
- This issue does not define automatic CUDA-versus-Arc benchmarking or policy.

## Execution Scope

- Add the OpenVINO Cargo feature and backend/configuration path.
- Preserve Candle Metal/CPU behavior and existing CUDA PR separation.
- Add tests for provider targeting, device resolution, fallback, identity, and
  readiness.
- Update README/runtime verification documentation.
- Verify on the NUC with real `[1,384]` embedding execution and record model,
  precision, shape, runtime, device, timing, and thermal conditions.
