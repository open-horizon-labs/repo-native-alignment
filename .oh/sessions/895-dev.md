## Design decisions

**1. Directory-level pruning vs. exact per-file counting.** The walk deliberately never descends
into an excluded/git-ignored directory (that's the whole performance point -- `target/` in this
repo is 3.9 GB / ~11.7k files). Counting individual files there via the normal walk would defeat
that optimization. Instead, `Scanner::count_pruned_subtree` does a *separate*, cheap
readdir-only recursion (no stat, no hash, no extraction) into a pruned subtree purely to attribute
every file beneath it to the class that pruned the directory. Measured cost: `find target -type f
| wc -l` (11,737 files) takes ~0.04s wall on this machine -- negligible next to the real scan's
per-file stat+hash+extract work. This is why `scan --timings` shows no material cost (below).

**2. Where the walk-level classes (`excluded_by_config`, `git_ignored`) live.** They are
recomputed fresh on *every* `scan()` call, full or incremental, and stored directly on
`ScanState` (`excluded_by_config_census` / `git_ignored_census`, each a bounded `{count, samples}`
struct capped at `CENSUS_SAMPLE_CAP = 20` paths). This works because the walk already re-visits
every non-pruned file on every scan (via `carry_forward_subtree`) even when extraction is
short-circuited for unchanged files -- only the *directory descent* is what mtime-based skipping
shortcuts, not the per-file/per-directory decision itself. So these two classes are trivially "the
full current population" on every call, by construction.

**3. Where the extraction-level classes (`indexed`, `binary_skipped`, `no_extractor`,
`extractor_error`) live.** Extraction only reprocesses changed+new files, so these classes CANNOT
be recomputed fresh every scan without re-extracting everything. Persisted per-file in
`ScanState.file_classifications: HashMap<PathBuf, FileClassification>` (one entry per file
currently in `file_mtimes` -- i.e., bounded by the same population `file_mtimes`/
`file_content_hashes` already track, not by anything under an excluded directory). Updated for
changed+new files after every extraction (`Scanner::apply_file_classifications`, merge) or fully
replaced after a whole-root re-extract (`Scanner::set_file_classifications`, e.g. the
cache-miss/full-build path in `build_full_graph_inner`); entries for deleted files are dropped
(`Scanner::remove_file_classifications`). This is the "persisted scan state is the obvious
carrier" answer the issue asked for, and it's what makes an incremental scan report the *full*
population rather than the delta -- proven by
`incremental_scan_reports_full_population_not_delta` (unit test) and by the real end-to-end proof
below (second `Files:` count == first, not 1).

**4. `no_extractor` reason.** `extract_file_classified` (new, alongside the now-thin
`extract_file`) tracks three things while iterating extractors: whether any extractor's
`extensions()` claimed the file's extension, whether any claiming extractor's `can_handle`
returned true, and whether any `extract()` call succeeded. `no_extractor` with detail "extension
not claimed by any registered extractor" vs. "extension claimed but declined by can_handle:
<names>" are the two cases the issue asked to distinguish; both are visible in the detail view.
A file where one extractor succeeds and another (matching) one declines or errors is still
`indexed` -- partial success means the content did make it into the graph.

**5. Rendering: read persisted `ScanState` from disk, not the live in-memory `ScanStats`.** The
existing `Encoding:` line reads `ScanStats` (an `Arc<RwLock<>>` populated by the event bus during
a live scan in the *same process*), which is empty for a fresh CLI invocation of `list-roots` that
didn't just run a scan. The issue explicitly wants the census durable across scans/restarts, so
`render_files_census_line` in `src/service/roots.rs` reads `scan-state.json` straight off disk
(new `crate::scanner::load_scan_state_from_path` / `primary_state_path`), mirroring the
primary-vs-declared-root path split `bg_scanner::scan_roots` already uses
(`.oh/.cache/scan-state.json` vs. `~/.local/share/rna/cache/{slug}/scan-state.json`). This means
`list-roots` shows the census even without a live server process, and is what the "clean cache,
full scan, then `list-roots` in a fresh invocation" proof below exercises.

**6. On-demand detail view: `search(mode="skipped", kind="<class>")` over a new `list_roots`
parameter.** Chose `search(mode=...)` because it's the codebase's existing pattern for exactly
this shape of request (`impact`, `doc_drift`, `cochange` all live in `search_traversal` and are
selected by `mode`), it gets CLI/MCP parity for free (both already thread `mode`/`kind`/`limit`
through to `SearchParams` for other modes), and it needed zero new MCP tool-schema surface (no new
field, no schema update) since `kind` and `limit` were already generic pass-through parameters.
A `list_roots` parameter would have required a new parameter on that tool's schema instead of
reusing wiring that already exists end-to-end.
