# #897: Surface artifact notes on bound code symbols

## Verification: did code-symbol targets resolve today?

No. `emit_local_knowledge_graph` (`src/extract/markdown.rs`) always emitted its
relationship edge with `to` pointing at a synthetic placeholder `NodeId` --
`root: ""`, `kind: NodeKind::Other(target.kind)` -- built purely from the
frontmatter text, with no cross-file graph visibility (it runs per-file,
during single-file extraction). For a code-symbol target (`kind: function`),
the placeholder's `kind` is `Other("function")`, which never equals a real
code node's `NodeKind::Function`, so the edge could never resolve to an
existing node, regardless of whether the named symbol existed. The edge was
also always `Confidence::Detected` with an evidence diagnostic
(`content.metadata_without_body_evidence`) marking it as nomination-only --
this is by design for the existing local-knowledge-node-to-local-knowledge-node
case (needs a body-evidence pack rule per #715), but nothing existed to ever
promote a code-symbol target specifically.

## What already existed vs. what I added

**Already existed:**
- `rna:` frontmatter parsing, local-knowledge node emission, and the
  frontmatter-candidate edge (`src/extract/markdown.rs` `emit_local_knowledge_graph`).
- The `content.*` diagnostic convention on nodes (`validation_status`,
  `diagnostic_code`, `diagnostic_severity`, `diagnostic_message`), demonstrated
  by `markdown_anchor_pass`'s `content.unresolved_anchor` for dead heading
  anchors -- reused verbatim for code-symbol relationships
  (`content.unresolved_relationship`).
- `doc_drift::leaf_identifier` and `doc_drift::is_code_symbol_kind`, solving
  the identical owner-qualified-name and code-symbol-universe problems for a
  different resolver. Both made `pub(crate)` and reused, not reimplemented.
- `format_node_entry_with_root` compact/detailed code rows, `repo_map`'s top
  symbols list, `GraphIndex` incoming-neighbor traversal.

**Added:**
1. `local_knowledge_symbol_binding_pass(&mut all_nodes, &mut all_edges)`
   (`src/extract/markdown.rs`) -- a new post-extraction pass, wired into
   `EnrichmentFinalizer::run_passes` (`src/extract/consumers.rs`) right after
   the existing ADR/anchor passes (same stage, same "needs full node
   visibility" requirement). It rewrites the specific placeholder edges
   `emit_local_knowledge_graph` produces for code-symbol targets
   (identified by `evidence[0].rule_id == "frontmatter-candidate@1"` +
   `to.kind` being `Other(<code-kind-string>)`) in place:
   - exactly one exact-name match in that (root, file, kind) -> rewrite `to`
     to the real `NodeId`, promote to `Confirmed`, clear the diagnostic.
   - exact match fails, retry against `doc_drift::leaf_identifier` of each
     candidate (owner-qualified names since #859) -- exactly one leaf match
     resolves the same way.
   - zero or 2+ matches -> edge left dangling (no confirmed edge to either
     candidate); the *local-knowledge node* gets
     `validation_status: unresolved` / `diagnostic_code:
     content.unresolved_relationship` / `diagnostic_severity: error`.
   - Non-code-symbol relationship targets (other artifacts, `uri:` cloud
     identities) are untouched -- the lookup key simply never matches
     anything in the code-symbol index.
2. Also surfaced the artifact's top-level frontmatter (`id`, `title`,
   `statement`, ...) onto the local-knowledge node as `frontmatter.<key>`,
   mirroring the existing convention `MarkdownExtractor::extract` already uses
   for `MarkdownSection` nodes. This exists so a guardrail's one-line
   `statement` (or a metis/signal's `title`) -- exactly the human-written
   summary these artifacts already carry -- can be preferred over the raw
   body for the rendered excerpt. Still verbatim artifact text, just a
   different declared field; the guardrail this feature is proven against
   (`computed-but-not-delivered.md`) has a list-heavy body with no natural
   first sentence, and `statement` is precisely what a human would want shown.
3. Rendering (`src/server/helpers.rs`):
   - `is_notes_source`: allowlist -- `local_knowledge` metadata, or
     `MarkdownSection` with `oh_kind` in `{metis, guardrail, signal, outcome}`.
     Synthetic `Other(_)` nodes (LSP diagnostics, co-change file anchors,
     frameworks) are never tagged `local_knowledge` and are excluded.
   - `collect_artifact_notes`: joins `GraphIndex` incoming `References`
     neighbors against an already-loaded node lookup (a closure, so callers
     reuse `GraphState::node_index_map()`'s existing cache -- no new
     allocation, no per-row file I/O).
   - `note_identity` / `note_excerpt` / `first_sentence` / `append_notes`:
     bounded `Notes:` block (max 3, `+M more`) and compact ` notes:N` marker.
     `first_sentence` skips leading Markdown headings and treats numbered-list
     markers (`1.`) as non-terminal, so `## Rule\n\n1. **Do the thing.**
     Rationale...` excerpts "1. **Do the thing.**", not "1.".
   - `format_node_entry_with_root` gained a trailing `notes: &[&graph::Node]`
     parameter (all ~20 call sites updated; most pass `&[]`, the two
     production code-symbol-row call sites in `src/service/search.rs`
     (`search`'s flat code-symbol section, and `search --nodes` batch
     retrieve) and `repo_map`'s top-symbols row (`src/service/repomap.rs`)
     compute real notes via `collect_artifact_notes`).
4. `docs/extractors.md` gained "Binding a note to a code symbol"; the
   `record` skill (`plugin/skills/record/SKILL.md`) gained a short pointer +
   example for metis/signal/guardrail authors, both cross-referencing each
   other.
5. `scripts/test-suite.sh`: unconditional check for
   `local_knowledge_symbol_binding_pass` (structural), plus a real
   end-to-end section right after Core Search (before any full/non-extract-only
   `scan` runs elsewhere in the suite -- see Friction below) asserting the
   real bound guardrail's `Notes:` block and `notes:1` marker.

## Cost

Rendering only joins already-loaded `GraphIndex` edges plus a cached
`stable_id -> index` map (`GraphState::node_index_map()`, built lazily once
per snapshot, already used elsewhere in `search.rs`). No new per-row file
I/O; artifact node bodies are already in memory as part of the loaded graph
snapshot (no additional cache needed). `scan --timings` unaffected --
`local_knowledge_symbol_binding_pass` runs once per scan over the full node
set, same order of work as the pre-existing `adr_validation_pass` it sits
next to.

## Friction / non-obvious finding

Cross-file resolution (artifact -> code symbol in a *different* file) only
sees nodes present in a single `EnrichmentFinalizer::run_passes` invocation.
During manual verification, an *incremental* scan (the suite's own
pre-flight, and any plain `scan --repo X` without `--extract-only`) left the
edge unresolved even though a clean scan resolved it correctly every time --
most likely the changed artifact file and the changed code file landing in
different partitions of the same incremental scan (a structural-cache
concern, not specific to #897 -- `adr_validation_pass`, which this pass sits
right next to and shares the exact same "needs the full node set" precondition,
has the identical exposure). Mitigated in the test-suite check by forcing a
clean scan (`rm -rf .oh/.cache` then a plain `--extract-only` scan) and
running it *before* any later full scan in the suite that could spawn
background LSP/embedding enrichment and race a later re-persist. Did not
chase this further since it's an existing incremental-scan property shared
with a pre-existing feature, not a #897 regression -- flagging for whoever
next touches incremental-scan partitioning.

Also found and fixed a bug in my own first draft: `first_sentence` naively
looked for `.`/`!`/`?` followed by whitespace, which stopped dead at
numbered-list markers (`1. Add extraction...` reads "1." as end of sentence)
and inside Markdown bold/code spans (`**text.**` -- the character after `.`
is `*`, not whitespace). Fixed by skipping closing Markdown emphasis/code
markers before checking for whitespace, and treating a token immediately
before punctuation that is *only* digits as a list marker, not a sentence end.
